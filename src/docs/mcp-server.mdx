# MCP Server

`@pulseui/react` ships a read-only [Model Context Protocol](https://modelcontextprotocol.io)
server, so an AI coding assistant can look up real component props, variants, sizes and
usage examples instead of guessing or hallucinating an API that doesn't exist.

It's **embedded in the package itself** — there's no separate `@pulseui/react-mcp` package
to install. It only works once `@pulseui/react` is already a dependency of your project.

---

## Prerequisites

```bash
npm install @pulseui/react
```

The server binary (`pulseui-react-mcp`) is installed into your project's `node_modules/.bin`
as part of that install — `npx pulseui-react-mcp` (used below) resolves it from there.

---

## Connecting a client

Every MCP-compatible client reads the same JSON shape; only the file location differs.

### Claude Code

Add a `.mcp.json` file at the root of your project:

```json
{
  "mcpServers": {
    "pulseui-react": {
      "command": "npx",
      "args": ["pulseui-react-mcp"]
    }
  }
}
```

Or register it without creating the file by hand:

```bash
claude mcp add pulseui-react -- npx pulseui-react-mcp
```

### Claude Desktop

Edit `claude_desktop_config.json` (macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`;
Windows: `%APPDATA%\Claude\claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "pulseui-react": {
      "command": "npx",
      "args": ["pulseui-react-mcp"]
    }
  }
}
```

Restart Claude Desktop for it to pick up the new server.

### Cursor

Add the same shape to `.cursor/mcp.json` in your project (or `~/.cursor/mcp.json` to make it
available in every project):

```json
{
  "mcpServers": {
    "pulseui-react": {
      "command": "npx",
      "args": ["pulseui-react-mcp"]
    }
  }
}
```

### Any other MCP client

If your client isn't listed above, it almost certainly accepts the same `mcpServers` object —
check its docs for where that config file lives.

---

## What it exposes

Two read-only tools — nothing here writes to your project or makes a recommendation:

<table className="token-table">
  <thead>
    <tr>
      <th>Tool</th>
      <th>Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><code>list_components</code></td>
      <td>Lists every component with its category and a short description. No arguments.</td>
    </tr>
    <tr>
      <td><code>get_component(name)</code></td>
      <td>Full details for one component: props (with types, defaults, descriptions), variants, sizes, accessibility notes, and real usage examples pulled from its Storybook stories.</td>
    </tr>
  </tbody>
</table>

`get_component` matches names case-insensitively and suggests the closest match if you get
the name wrong (e.g. `"Buton"` → suggests `"Button"`).

Neither tool recommends *which* component to use for a given task — that decision is always
left to you or your assistant's own judgment, not the server.

---

## Trying it without a client

Inspect the server directly with the official [MCP Inspector](https://github.com/modelcontextprotocol/inspector),
no client config needed:

```bash
npm run build
npx @modelcontextprotocol/inspector node dist/mcp/server.js
```

This opens a local web UI where you can call `list_components` and `get_component` by hand
and see the raw JSON response.

---

## Keeping it accurate

The data these tools serve comes from `src/mcp/components-data.json`, generated by parsing
every component's TypeScript props, JSDoc and Storybook stories — it's never edited by hand.
If you're contributing a component, see
[Contributing](?path=/docs/guide-contributing--docs) for when to regenerate it.
